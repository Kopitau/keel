# RES-902 全局安装器 + 项目内运行的分发形态

## 调研问题

用户要求「类似 Trellis，在项目文件夹激活就等于部署」。需要回答：

1. 全局命令与「项目内 vendored 副本」能否共存？
2. npm 的 bin 能否指向 `.ts`（DEC-151 免构建）？Windows 上生成的 shim 是否可用？
3. 不公开发布到 npm registry 的前提下，如何分发全局命令？
4. Trellis 的命令面是什么样，有哪些值得照抄？

## 检索范围与方法

- **本机一手实测**（Windows 10，Node v22.19.0，npm 全局目录 `AppData/Roaming/npm`）；
- 本机已安装的 Trellis v0.6.5 包（`package.json`、`bin/trellis.js`、`trellis --help`）作为对照实现；
- keel 现有实现（`tools/gate/ctx.ts`、`gate.ts`）。

## 证据

### 1. 现状：gate 认自身位置，不认当前目录

`gate.ts:40` 用 `repoRootFromGateFile(import.meta.url)` 定 root。实测：在别的项目目录下调用 keel 的 gate，`root` 仍指向 `E:\program\en`。

→ **不能简单把现有 gate 放进 PATH**，那样它只会操作 keel 自己。

### 2. 关键洞察：只有 `init` 需要感知当前目录

Trellis 的 `init` 本质也是把文件复制进目标项目；装完后项目里有自己的一套。因此：

- `init` / `update` / `uninstall`：源 = 命令自身位置，目标 = **当前目录**；
- 其余全部命令：仍由项目内副本执行，root 解析逻辑**一行不用改**。

**这使「全局分发」与「vendored 运行」不再是二选一**，DEC-153 的实质理由（离线可用、版本随项目锁定）全部保留。

实测验证 cwd/self 分离成立：从目录 A 调用位于目录 B 的脚本，`process.cwd()` = A，`import.meta.url` = B。

### 3. npm bin 指向 `.ts`：Windows 上可行（实测）

构造测试包，`bin` 同时提供两种入口，在另一项目里 `npm install <本地路径>`：

| 入口形态 | 生成的 shim | 运行结果 |
|---|---|---|
| `bin/keel.js`（薄壳 → 动态 import `.ts`） | `kt-js` / `.cmd` / `.ps1` | ✅ 正常，cwd = 调用目录 |
| 直接指向 `src/cli.ts` | `kt-ts` / `.cmd` / `.ps1` | ✅ 正常，cwd = 调用目录 |

→ **免构建（DEC-151）可以保住**，不需要为分发而引入编译步骤。

### 4. 重要发现：应选 `.js` 薄壳而非直接 `.ts`

虽然两者都能跑，但**直接把 `.ts` 作为 bin 入口会破坏 DEC-150 的友好拒绝**：

- DEC-150 要求低于 Node 22.18.0 时给出明确错误（现有 `gate.sh` 就是这么做的）；
- 若 bin 直接是 `.ts`，旧版 Node **在解析阶段就语法报错**，用户看到的是难懂的 SyntaxError，而不是「需要 Node ≥22.18.0」。

→ 采用 Trellis 同款模式：`bin/keel.js` 为**纯 JS 薄壳**，先做 Node 版本检查，通过后再 `import()` `.ts` 主体。Trellis 的 `bin/trellis.js` 正是三行薄壳（`#!/usr/bin/env node` + 动态 import）。

### 5. 分发渠道：不必公开发布

| 方式 | 命令 | 适用 |
|---|---|---|
| git URL 全局安装 | `npm i -g git+https://<host>/<org>/keel.git` | 团队标准做法；需要远端（当前未配，见 ISS-016） |
| 本地路径全局安装 | `npm i -g file:E:/program/en` | 远端就绪前的过渡 |
| 公开 npm registry | `npm i -g keel` | 有外部用户时才需要，非必需 |

**[未核实]**：`npm i -g file:...` 在本机是复制还是链接（影响「改仓库是否立刻改变全局命令」）；Gitee 私有仓库 `git+https` 全局安装的鉴权方式。落地时实测。

### 6. Trellis 命令面（对照实现，`trellis --help`）

核心四个：`init`（在当前项目初始化）/ `update`（把项目内文件更新到最新）/ `upgrade`（升级全局 CLI 本身）/ `uninstall`（从项目移除）。

**值得照抄的一点**：把「更新项目文件」与「升级 CLI 本身」分成两个命令（`update` vs `upgrade`），语义清晰、不会误操作。

## 结论（决定／理由／备选）

- **决定**：采用**全局安装器 + 项目内运行**的双层形态。`bin/keel.js` 纯 JS 薄壳（版本检查 → 动态 import `.ts`），提供 `init` / `update` / `uninstall`（作用于当前目录）；其余命令仍由项目内副本执行。分发先用本地路径/git URL 全局安装，不公开发布。
- **理由**：实测证明 npm bin 指向 `.ts` 在 Windows 可行，免构建保得住；`.js` 薄壳保住 DEC-150 的友好版本拒绝；只有 init 类命令感知 CWD，现有 root 解析零改动；vendored 的离线与版本锁定优势全部保留。
- **备选**：① 单文件安装器 `node <keel路径>/install.mjs`（不与任何决策冲突，但要知道 keel 在哪，达不到「在项目文件夹激活」的体验）；② 全面改为 npm 运行时分发（放弃 vendored，失去离线与锁定优势，未采纳）。

## 剩余不确定性

- 上述 **[未核实]** 两项（本地路径全局安装的链接语义、Gitee 私有仓鉴权）；
- macOS/Linux 上 npm bin 的可执行位与 shebang 行为未实测（预期正常，与 ISS-004 同源需注意）；
- `init` 写入前若目标目录已有 `keel/config.json` 的处置（k-init 技能已规定"停止并改用 k-change/k-impl"，实现需遵守）。

## ISS-022 更正（2026-08-25）

§3「npm bin 指向 `.ts` 在 Windows 可行」只覆盖了 **junction/链接** 安装（文件不在 `node_modules` 真实路径下）。真副本（tarball / git URL）会落入 `node_modules`，Node **拒绝**对该目录做类型剥离（`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`）。安装器层（`bin/` + `tools/cli/`）必须是纯 JS；复制进项目的 `tools/gate/*.ts` 不在 `node_modules` 下，DEC-151 仍然成立。`private: true` **不阻止** `npm i -g`（复审代测）。
