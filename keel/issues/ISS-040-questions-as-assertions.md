# ISS-040 访谈把「问题」写成「主张」——用户只能点头，无从判断（重复发生）

## 现象

zhaoxi 的需求访谈，一条消息 5946 字、30 个编号的「Q」，**全文只有 7 个问号**。典型条目：

> Q13 领域模型。推荐：一个条目属于且仅属于一个领域+一个细分。备选：多对多。

这不是问题，是一条已经做好的决定加一个脚注。用户能做的只有整体接受或整体推翻，无法针对取舍本身发表意见。同一批条目里 inbox、Ctrl+K 面板等术语首次出现即使用，未作解释；用户在 67 分钟后才问出「什么是 Inbox」。

复现：读 `C:\Users\NF3317\.claude\projects\E--program-zhaoxi\b14ac2e3-*.jsonl`，统计该条消息的 `?` 与 `Q\d+` 计数。

## 根因

C-02 的规则原文是「batch every currently askable question **each with a recommended answer**」。这句话**只约束了"要带推荐"，没约束"必须是问句"**——而"带推荐"这个要求本身就在把写法往主张的方向拉：先写结论、再补一句备选，比先构造问句省事得多。

规则的措辞在无意中鼓励了它想防止的行为。

## 这是重复发生（C-61）

**上一次**：2026-08-24，用户对本框架的设计复审者说——

> 确认的部分太简短了，以后确认的部分背景和说明需要详细一点

同一个指纹：把需要用户判断的取舍，压缩成用户只能点头的形态。

**上次的防线为什么失效**：当时的处置是把它写进了**复审者的个人记忆文件**（`memory/feedback-decision-presentation-detail.md`），而不是框架。个人记忆只对那一个 agent、那一条会话线有效；zhaoxi 是另一个项目、另一个上下文，它读不到，也没有任何机制让它读到。

**防线放错了层**：这是一条关于"访谈该怎么写"的通用纪律，本来就该在 k-grill 里，却被当成了"某个模型的个人偏好"。

## 修复

`.agents/skills/k-grill/SKILL.md` 新增 "How a question must be written" 节，三条硬要求 + 一组正反例：

1. 每条必须是**疑问句、以 `?` 结尾**；推荐是附加物，不能取代问题
2. 首次出现的术语必须先解释
3. 每个选项要写清代价，不只写偏好

并给出**自检**：发出前数问号——问号数少于编号条目数，说明有条目写成了主张，重写。

正反例直接用 Q13 这个真实案例改写，因为抽象规则挡不住"我觉得我写的够清楚了"。

## 为何未被更早发现

访谈发生在对话里，**不落盘**。门禁看不到任何一个字，五层执法在这里只有 L0 一层可用。六轮复审全部针对落盘产物，从未审过"提问的形态"。

## 闭环选择与理由

选**项目规则**（技能措辞），并明确承认这是可用档位里最弱的一档。更高的三档在这里都不可行：

- 回归测试 / lint：没有被测对象，访谈不产生文件
- 门禁 / hook：同上

考虑过的替代方案：要求访谈问题也落盘成文件再受检。**否决**——那会把一次对话变成一轮文件往返，违背 F5 的框架开销控制，也让访谈变得比现在更难用。

已做的次强措施：`tests/r6-field-guards.test.ts` 有两条断言，钉住这段规则文本不被悄悄删掉（守的是规则的存在，不是规则的遵守）。

**残余风险照实说**：模型仍可能不遵守。这条防线的强度上限就是"下一个读 k-grill 的 agent 会不会认真读"。若再次发生，按 C-61 应升级——届时的升级方向是把访谈提纲作为文件产出纳入门禁，接受那笔开销。
