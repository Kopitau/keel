# ISS-003 追溯对账未接入门禁，10/24 需求零测试覆盖而门禁全绿

## 现象

`gate trace` 自己报告 `uncovered: 10 / 24`，但 16 项门禁检查中**没有任何一项消费追溯结果**。C-32 的确认原话是「按验收标准逐条对账，验收范围内零引用=门禁不过」。此外追溯只做到需求级（`## REQ-\d{3}`），未解析每条需求下的 GWT 验收标准，等于把「逐条对账」降级成「有没有被提到」。搜索根还包含 `tools/gate/`，源码注释里出现 `REQ-nnn` 就算「有覆盖」。

复现命令：

```bash
node tools/gate/gate.ts trace | tail -3        # uncovered: 10 / 24
node tools/gate/gate.ts check | grep -ci trace  # 0 —— 门禁里没有追溯项
```

## 根因

`trace.ts:20` 只按需求标题建行；`trace.ts:56-79` 的 `runTrace` 无论多少未覆盖都 `return ok()`；`check.ts:382-403` 的检查清单里没有追溯项。

## 修复

1. 新增门禁项 `X-trace`：验收范围内的需求若零覆盖 → FAIL；
2. 追溯粒度下沉到验收标准（解析 `- Given … When … Then …` 行），对账到条；
3. 搜索根限定为测试目录，排除 `tools/`，避免源码注释冒充覆盖；
4. 当前 10 条未覆盖需求（REQ-002/003/005/007/008/009/010/013/014/022）全是**流程类功能**，其验收方式取决于 ISS-006（C-139 技能验收），两者需一起解决。

## 为何未被更早发现

追溯功能做了、命令能跑、输出也正确，但从未接进裁决路径；而门禁自身没有「所有 gate 命令的产出都必须被消费」这类元检查。

## 闭环选择与理由

**回归测试** + **门禁项**：新增 `X-trace` 检查，并配负面测试（构造一条无覆盖需求 → check 必须 FAIL）。

闭环：搜索根仅 `tests/`。验收范围=有 `summary.md` 的功能其 `req:`（C-32）。未宣称完成的 10 条流程 REQ 仍无测试，留给 P2-1 / C-139，不在本条用 skip 假装覆盖。
