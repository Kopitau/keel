# DEC-160 评审视角按代码性质分类

## 问题

复审者在提议自动评审回路时，要求评审「必须做实证攻击」并维护一张攻击面清单。用户指出这是**过度泛化**：攻击面框架来自审 gate 自身（执法机制的核心问题就是能否被绕过），但对普通功能代码，假想有人攻击没有意义，真正该问的是鲁棒性。

## 选项对比

| 选项 | 说明 | 问题 |
|---|---|---|
| A 一律走攻击面 | 复审者原提议 | 给 CLI 包装做安全审计，仪式过重，与 C-41「不吹毛求疵」冲突 |
| B 一律走需求达成 | 最轻 | 门禁代码只走 happy path —— 这三轮的阻断级问题一条都发现不了 |
| **C 按代码性质分类**（选定） | 门禁类走攻击面、核心级走鲁棒性、辅助级走需求达成 | 需要一个分类轴 —— 复用已确认的 C-31 测试分级即可，不另造 |

## 推荐理由

两类视角底下是**同一条纪律**：不只走 happy path，主动构造让它失败的情形，且必须实证而非读代码推理。区别只在「失败」的构造方式——对门禁叫攻击（能否被单方面绕过），对功能叫边界与异常（脏数据、依赖挂掉、中途失败）。分类复用 C-31 避免引入第二套判定轴。

## 用户决定原话

「有些是功能实现，也需要攻击面么？很多时候只需要满足这个功能就行了，而不是假想会被攻击。或者说稳定性（鲁棒性如何）」（2026-08-24）

## 影响

| 代码性质 | 视角 | 检查项 |
|---|---|---|
| 门禁 / 证据 / 审批 | **攻击面** | 改配置、伪造证据、缩范围、删测试、消警告、绕 hooks——须在临时副本实际尝试并记录复现命令 |
| C-31 **核心**级 | **鲁棒性** | 边界输入（空/超长/特殊字符/非 ASCII/极值）、依赖不可用、脏数据、并发或重跑、**中途失败是否留下半成品状态**——须实际构造运行 |
| C-31 **辅助**级 | **需求达成 + 明显错误路径** | 验收标准逐条对上；参数缺失/格式错时是人话还是堆栈 |

- 分类由**被改动文件的性质**决定，不由实现方自述；跨类别改动按最严的一类处理。
- 攻击面清单**随每轮新发现追加**，使经验固化——子代理每次都是新的、没有跨轮记忆，清单是唯一的经验载体。
- 三类一律遵守 C-41：只报影响正确性与需求达成的问题。
