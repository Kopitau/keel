# DEC-183 keel 减重：门禁留 8 条骨架、预提交只跑秒级检查、评审改为方案级一轮、记录三合一

## 问题

用户："感觉目前的架构很沉重，让 agent 运行代码的时候经常会有摩擦，效率很低。同时结果汇报也不清晰。是不是记录和验证的部分有过度设计？"

诊断：原则（留痕 / 验证 / 审批 / 复用）没有过度，**机制**过度——每出一次事故加一条机器规则（22 条门禁、6005 行 gate、321 条自测），同一件事写四遍，不可变用到元数据，工作树一脏全检必红，预提交跑全量测试，评审每功能多轮。数字与来源见 CHG-011 动机节。

## 选项对比

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 原则留、机制砍半 | 摩擦源逐一消除；留下的都是这周真拦过谎报的 | 触碰十余条已确认规则与多条 REQ，要出 v5 |
| B. 只改汇报层 | 成本最低 | 重量不变 |
| C. 维持现状 | 无 | 摩擦持续，红灯常态化 |

门禁的两种砍法：

| | 甲 全删 | **乙 留骨架** |
|---|---|---|
| 形状 | 去掉 `tools/gate`，只剩记录 + 技能 | 留 8 条（基线存在、计划唯一、证据绑树哈希、追溯、绕过检测、审批身份、完成、合并），删 14 条 |
| 代价 | "完成"回到 agent 自报 | 每次提交几十毫秒 |

评审时机的代价：改为方案级一轮后，zhaoxi F0 那类在第一个功能就被抓出的锁 TOCTOU、备份天花板会到方案末尾才发现，修起来牵连更多。

## 推荐理由

A + 乙。留下的 8 条是这周三次"说修好了其实没有"的抓手，成本可忽略；删掉的 14 条全是判记录形状的规则，误杀三次、拦住的真问题零。评审方案级一轮由用户明确接受其代价。

## 用户决定原话

> A 门禁删掉 预提交是什么？ 可以 可以 可以 技能不用合并。同时测试应该按照验证功能（沟通的小功能也需要测试）。子agent审核不用每个功能都审核，而是整个技术方案都实现了再进行审核。

> 乙 接受这个末尾才发现的代价

## 影响

见 CHG-011（删除 / 修改 / 新增 / 影响评估）。本决定是 CHG-011 的依据；需求 v5 与规划 v4 待 CHG-011 批准后出。

自主实施回路（用户重点说明）：k-new 一次点头之后，agent 实现 → 测试 → 记录 → 功能完成时压缩 worklog 进 summary → 自动下一个功能（新上下文只读压缩记录）→ 全部完成后子代理评审 → 用户验收；人只在不确定、断点、验收三处出现。k-impl 的"切完就停"改为"切完就继续"。

## 后果与复审条款

- 难逆转：删掉的门禁模块与自测不会自动回来；消费项目升级后同步减少。
- 无上下文会意外：为什么一个强调"证据不靠宣告"的框架只留 8 条门禁——因为另外 14 条判的是记录的形状，不是完成的真假。
- 真权衡：更少的机器规则 ⇄ 更依赖方案级评审与人的验收。
- 复审触发：方案级评审连续两次在末尾发现"早该在第一个功能抓到"的缺陷 → 重新考虑"每波次一轮"；或某项目再出现"说修好了其实没有"而 8 条门禁没拦住 → 对该形态补一条，而不是恢复 14 条。
