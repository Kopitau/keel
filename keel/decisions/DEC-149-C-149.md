# DEC-149 gate 运行时改为 Node + TypeScript（取代 DEC-101）

## 问题

gate 的运行时选 Python 还是 Node+TS？原决策 DEC-101/C-101 选 Python ≥3.11 仅标准库。

## 选项对比

**Python ≥3.11 stdlib**（原决策）：团队技能匹配、无构建步骤；但目标机器不保证有 Python 3.11+。

**Node + TypeScript**（本次选定）：① **六个目标 harness 里五个是 npm 包**（Claude Code、Codex、OpenCode、DeepSeek Harness、Pi）——凡能跑 keel 目标平台的机器必然有 Node，Python 则不保证；② 类型检查减少一类运行时错误；③ npm/npx 是该生态的原生分发渠道。

**实测证据（2026-08-21 本机 Windows，Node v22.19.0）**：Node 22 原生剥离类型，**可直接运行 `.ts` 文件，零构建步骤、零依赖**；启动开销 .ts 231ms vs .js 245ms（15 次平均，含 Windows 进程创建成本），差异在噪声范围内。对照：`python -c pass` 224ms、`git status` 368ms——**语言选择对流畅度的影响远小于一次 git 调用**。

## 推荐理由

我原推荐维持 Python（团队技能匹配）。用户在了解权衡后选择 Node+TS，理由成立：跨 harness 生态一致性（Node 必然存在）优先于团队语言偏好。关键顾虑（TS 需构建，或用 tsx 拖慢 300-500ms）已被 Node 原生类型剥离的实测排除。

## 用户决定原话

「同时改为node+ts」

## 影响

**取代 DEC-101/C-101**。gate 运行时 = Node + TypeScript，保持「零运行时依赖（仅 Node 内置模块）」与「一份实现五处调用」两条原则不变。

连带影响：① W1 已产出的 `tools/gate/gate.py`、`tools/bootstrap/w1_bootstrap.py`、`tests/test_w1_skeleton.py`、`pytest.ini` 需以 TS 重做（gate.py 仅 54 行桩，成本低；bootstrap 已完成使命可归档）；② `keel/config.json` 的 `profiles.active` 需改；③ 框架自身测试画像（DEC-126、DEC-139）中「gate=pytest」改为 Node 侧方案；④ 分发方式、Node 版本基线、测试运行器、类型检查门禁为本决策派生的待确认子项，见 CHG-001。

## 后果与复审条款（adr）

**后果**：keel 与 npm 生态绑定；团队（以 Python 为主）维护 gate 需具备 TS 能力；换回 Python 的成本随 gate 代码量增长而上升。

**复审触发条件**：① Node 移除或改变原生类型剥离行为（届时需重新评估构建步骤）；② 团队实际维护中出现明显阻力；③ 目标 harness 生态发生迁移（如主要 harness 不再以 npm 分发）。
