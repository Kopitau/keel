# DEC-161 首次真实使用后的四条防线

## 问题

keel 第一次被用在真实业务项目（zhaoxi，2026-08-25）上，暴露出四处「规则在、执法不在」。四处都触及已确认的判定机制（C-04/C-05/C-06/C-11 与 k-grill 技能文本），要拍板的是：**每一处该把防线放在哪一层**，以及能不能接受随之而来的摩擦。

背景：按 C-59 闭环阶梯，问题必须转化成可执行的防线（回归测试 > lint > 门禁/hook > 项目规则 > 决策修订 > 显式不修），"记录下来以后注意"不算闭环。

## 选项对比

| 选项 | 优点 | 缺点 |
|---|---|---|
| A 只改技能措辞（L0） | 零摩擦，改起来最快 | 四条里三条本来就有规则，失效的正是 L0；等于原地踏步 |
| B 四条全部上门禁/测试，能机检的都机检 | 真正阻断；早期阶段不再廉价绿灯 | 存量 RES 全需补表态；判据设计不当会误杀 |
| C 只做机检成本最低的两条（顺序、OSS 表态） | 摩擦最小 | 缺口猎取仍然做没做都一样，问题最大的一条反而不管 |

## 推荐理由

选 B。四条里有三条可以机检，把它们留在 L0 等于承认规则只是建议。唯一不可机检的是访谈写法（对话不落盘，五层执法只剩 L0），对它必须诚实标注防线上限，而不是假装它和其他三条一样硬。

误杀风险是 B 的真实代价，处置方式写在 [[ISS-038]]：**新判据先拿现实中最好的样本实测再上线**——第一版缺口猎取判据就误杀了 zhaoxi 那份高质量产出，因此改为查实质不查格式。

## 用户决定原话

> 四条都做，同时你再调研一下这个对话记录，看还需要加什么功能修正

（四条防线的具体判据在提出时逐条给了背景、判据、改动位置与代价；用户在此基础上确认。）

## 影响

| 防线 | 层级 | 落点 | 判据 |
|---|---|---|---|
| 1 顺序倒置 | 门禁 + 回归测试 | `G-req` | 有 RES 而需求书不存在或 REQ 条目为 0 → FAIL |
| 2 缺口猎取 | 门禁 + 回归测试 | `G-req` ← `tools/gate/gaphunt.ts` | 有 confirmed 条目而无猎取记录 → FAIL；薄猎取 → FAIL；命名/署名异常 → WARN |
| 3 OSS 表态 | 门禁 + 回归测试 | `X-oss` ← `inspectResOss()` | RES 两个字段都空 → FAIL；悬空引用 → FAIL；不再因缺 package.json 而 SKIP |
| 4 访谈写法 | 项目规则 | `.agents/skills/k-grill/SKILL.md` | 疑问句 + 术语先解释 + 代价可见；配正反例与数问号自检 |

生效范围：全部消费项目。**存量迁移代价**：每份既有 RES 需补一行 `oss:` 或 `oss_none:`；已基线的需求书需补一份缺口猎取记录。本仓已自行完成（10 份 RES 逐份按实际结论表态；`gap-hunt-v3.md` 由未参与访谈的独立上下文实际产出，34 条发现）。

测试义务：`tests/r6-field-guards.test.ts`，17 条，含一条**误杀回归**——复刻 zhaoxi 真实产出的形状（`vN-gaps.md` + 表格 + 散文署名），断言 PASS。

## 后果与复审条款

**难逆转**：判据一旦上线，所有消费项目的既有 RES 和需求书都会立即变红，回退意味着再次接受"规则在、执法不在"。

**无上下文会意外**：`X-oss` 现在**不因缺 package.json 而 SKIP**——这与它原本的名字（看起来只管 npm 依赖）不符，新读者容易误以为没有清单就不用管。

**真权衡**：防线 4 的强度上限是"下一个 agent 会不会认真读技能文本"，明显低于其余三条。这个不对称是被接受的，不是被忽略的——理由与被否决的替代方案（访谈提纲落盘受检）记在 [[ISS-040]]。

**复审触发条件**：
- 防线 4 同指纹再次发生 → 按 C-61 升级，方向为访谈提纲落盘纳入门禁
- 任一防线出现误杀真实良好产出 → 立即按 [[ISS-038]] 的方式修判据并补样本回归测试
- 消费项目反馈存量迁移成本过高 → 重估是否给历史记录一个带理由的豁免通道
