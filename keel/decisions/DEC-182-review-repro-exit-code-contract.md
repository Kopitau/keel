# DEC-182 自动评审复现命令的漏洞态与修复态判定

## 问题

自动评审打开 blocking ISS 时会保存一条复现命令，修复后 `gate loop clear` 再跑同一条命令。但现有需求没有唯一规定“什么结果表示漏洞存在、什么结果表示已经修好”，机器可能把仍可复现的问题清零。应统一退出码约定，还是给每条 ISS 增加结构化谓词？

## 选项对比

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 统一“攻击探针”退出码约定 | 不增加 ISS 字段；同一命令即可完成打开与清零：漏洞可复现=`0`，已修复/攻击被拒=`非 0`；与现行 `gate loop clear` 实现一致 | 普通测试通常“失败=非 0”，评审者需要用一层 `node -e`/shell 包装成攻击探针语义 |
| B. 每条 finding/ISS 保存结构化 `vulnerable_when` 与 `fixed_when` | 可直接复用不同风格的测试命令；能表达指定退出码或输出匹配 | 新增记录字段、解析器、正则/跨 shell 规则与迁移；错误组合会扩大评审门禁攻击面 |

## 推荐理由

推荐 A。keel 的目标是薄流程层；一个固定退出码协议比可编程谓词更容易审计，也与现在的 `runReproCommand(): exit_code !== 0 => refused` 完全一致。为防止“命令写反”，ingest 应先在未修复树实跑：只有退出 `0`、确实重现问题时才自动开 ISS；clear 再要求同一命令变为非 `0`。

## 影响

- blocking finding 必须带“攻击探针”命令：未修复树上漏洞可复现时退出 `0`；修复后攻击被拒时退出非 `0`。
- ingest 必须先实跑探针；只有退出 `0` 才自动开 ISS。缺命令或首次已退出非 `0` 时不得开 blocking ISS，改记待核实并保留观测结果。
- clear 只在同一命令变成非 `0` 时通过，并把命令、退出码、时间、轮次和 tree hash 追加进证据。
- finding、ISS 不增加 `vulnerable_when` / `fixed_when` 字段；B 不实施。
- 必须新增正反向黑盒测试，证明命令写反、缺失或仍退出 `0` 时不能 clear。

## 后果与复审条款

- **难逆转**：消费项目的 ISS 与自动评审脚本会依赖该判定协议。
- **无上下文会意外**：“非零代表修好”与普通测试的直觉相反，必须在模板和技能中醒目标明。
- **真权衡**：固定约定更薄但需要包装命令；结构化谓词更灵活但增加协议和攻击面。
- **复审触发**：大量 finding 因包装困难无法提供探针，或需要判断退出码以外的多阶段外部状态时，重新评估 B。
