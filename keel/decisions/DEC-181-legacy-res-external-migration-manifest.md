# DEC-181 旧 RES 身份使用外置迁移清单

## 问题

DEC-176 要求升级前已有、正文零 URL 的标准/深度 RES 可以先 WARN，但必须有客观且持久的 legacy 身份。这个身份是逐份写回旧 RES，还是集中写在独立迁移清单里？

## 选项对比

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 使用外置迁移清单 | 不改历史 RES；一次升级可集中生成、审阅和校验 | gate 需要维护清单路径与哈希一致性 |
| B. 给每份旧 RES 增加 frontmatter 字段 | 身份跟记录放在一起，读取直接 | 会批量改写历史记录，也使“原内容”哈希与新字段互相缠绕 |

## 推荐理由

推荐 A。legacy 是一次迁移事实，不是研究报告本身的新结论；放在外置清单既能保留旧文件原貌，也能用规范化全文哈希防止旧身份被修改后的文件继续冒用。

## 影响

- 清单固定为 `<records_dir>/migrations/res-citation-legacy.json`（本仓解析为 `keel/migrations/res-citation-legacy.json`），独立于各 RES 文件。
- 客观迁移分界是项目从 `keel_version < 0.8.0` 升到 `>= 0.8.0`；版本从写入前的 `<records_dir>/config.json` 读取。缺失或不是合法语义版本时，update 必须拒绝迁移并保持零写入，不得由 agent 猜测。
- 每项至少记录 `id`、仓库相对 `path`、迁移时按 DEC-144 规范化后的全文 `sha256`；清单顶层记录生成它的源 keel 版本、目标 keel 版本与生成日期。相同 `path`/`id` 不得重复。
- `keel update` 在用户明确输入 `y` 后，才可把升级前已存在、标准/深度且正文零 URL 的 RES 加入清单；预览必须把清单的新增或变化列入覆盖清单，确认前零写入。
- G-research 只在“清单有唯一匹配项、路径存在、ID 一致、当前规范化全文哈希与迁移哈希一致、正文仍为零 URL”时给 WARN。
- 清单缺项、重复、路径/ID/哈希不符时 FAIL；记录补入合格 URL 后按新规则 PASS，并可由后续确定性维护步骤移除对应清单项。
- 旧 RES 本身不因这次迁移被修改。任何实质修改都会改变全文哈希，从而使 legacy WARN 失效并按新记录规则 FAIL，直到引用补齐。

## 后果与复审条款

- **难逆转**：消费项目一旦生成该清单，后续 gate 与升级器都会依赖路径、字段和哈希语义；改变它必须迁移存量清单。
- **无上下文会意外**：清单中的 WARN 不是永久豁免；任何正文实质修改都会因全文哈希变化而自动失效。
- **真权衡**：保留历史 RES 原貌与集中审计，换来一份必须长期校验和迁移的外置状态文件。
- **复审触发**：清单规模明显影响 gate 性能、records_dir 协议改变、或需要跨仓搬迁 RES 时，重新评估路径/主键与哈希材料；变更仍须走 CHG 并提供确定性迁移。

## 复核（2026-08-29，CHG-011 / DEC-183）

外置迁移清单 `keel/migrations/res-citation-legacy.json` 及安装器的 legacy 预览 / 写入随 CHG-011 删除；旧 RES 不再需要身份清单。 状态改为 superseded → DEC-183（CHG-011，APR-004）。
