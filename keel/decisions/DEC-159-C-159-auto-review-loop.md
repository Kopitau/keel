# DEC-159 F7 自动评审回路

## 问题

现状是人工居间转手：实现方说做完 → 用户叫复审者审 → 复审者写 ISS → 用户转告实现方 → 修 → 用户再叫审。三轮下来用户转了六次手。C-39（评审者隔离）与 C-42（复审用新上下文）本就允许「派干净子代理」，缺的只是把回路接起来、结论自动落盘。需定四件事：触发方式、异构策略、自动开 ISS 的门槛、谁判「清零」。

## 选项对比

**触发**：A 声称完成时自动触发（评审成为完成的必经步骤）／ B 仍由人手动触发／ C 按规模分流。
**异构**：A 默认同源、触及门禁与证据机制强制异构／ B 一律同源／ C 一律异构。
**落盘门槛**：带复现命令才自动开 ISS／ 全部自动开事后人工筛。
**清零判定**：复审子代理实跑每条复现命令确认被拒／ 评审子代理声明即可。

## 推荐理由

- **触发选 A** 的决定性证据：这三轮里实现方每次都诚实地自查了，**但自查从未发现这些问题**——不是态度问题，是自己审自己看不见自己的盲区。评审因此不该是可选步骤。
- **异构选 A**：门禁/证据/测试机制正是「同一模型可能有同样盲区」的地方；其余改动同源够用，省成本。
- **落盘门槛**：无复现命令即自动开条目会让问题库灌水、真问题被淹没；C-58 本就要求问题条目含复现命令，此处复用。
- **清零判定**：「评审说没问题了」本身也是自述。实跑复现命令是三轮复审里每次都做的事，应固化成规则。

## 用户决定原话

「1 A 2A 3 同意 4 同意」（2026-08-24），对应：触发方式 A、异构策略 A、落盘门槛按推荐、清零判定按推荐。

另：「等 grok 完成之后，将这部分接到复审的后面」——实施排期在 R3 复审之后。

## 影响

1. **触发**：实现方声称完成时自动派评审子代理；未经评审不得进入验收。
2. **异构**：默认同源干净子代理；触及门禁/证据/测试机制的改动强制换一家 harness 跑 headless 复审（C-40 的可选项在此类改动上升为强制）。
3. **落盘**：blocking + 有复现命令 → 自动开 ISS；无复现命令 → 降级「待核实」进 worklog。
4. **清零**：复审子代理必须实跑每条 ISS 的复现命令、确认被拒，结果写进证据。
5. **熔断**：同一条 blocking 修 3 轮未清零 → 停止回路、向用户报告三轮经过（初值 3，可调）。
6. **用户介入点**：由「每轮都要」降为「熔断时」与「清零后的验收（A4）」两处。**验收不自动化。**
7. **平台兼容**：有原生子代理则并行派，无则顺序开新会话（C-30 不变）。

## 后果与复审条款（adr）

**后果**：评审 token 成本从「按需」变为「每次完成必付」；换来的是用户不再逐轮转手，且评审不会被遗漏。自动回路若设计不当会空转烧钱，熔断是唯一刹车。

**复审触发条件**：① 熔断频繁发生（说明阈值或评审质量有问题）；② 评审子代理连续多轮零发现（说明评审流于形式，需检查清单是否失效）；③ 平台子代理能力变化。
