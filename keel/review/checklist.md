# 评审清单（REQ-028 v9 / CHG-017）

评审者只回答三个问题：读代码、读证据，最多把项目的测试命令跑一次（pack 里的证据对本树新鲜时连这一次也免）。按风险核对需求边界与失败路径，不主动扩成探针、突变或无关安全审计；同树证据不反复全量重跑。

## 三问

1. **规范与可维护**：代码是否规范、尽量简单、别人能看懂能改。重复实现、无必要的抽象或复杂度、超出计划范围的改动、该给人话错误的地方给了裸堆栈，都算。风格与命名口味不算。
2. **功能是否实现**：diff 是否做了规划义务与需求条目说的事，有没有做规划禁止的事。对照 pack 里的 `plan` / `reqs` 读，不靠猜。
3. **功能测试是否写了、是否通过**：按每条验收的 verification 类型判断：auto 需要公共接口上的行为测试；machine-doc 需要相关的可运行文档/协议检查；manual 需要真实人工或环境证据，缺少则明确列为未完成的验收条件。REQ-nnn/AC-i 与 feature_coverage 是追溯映射，不自动证明测试质量；文档匹配不能证明模型真的按指令完成了任务。跳过或替换测试有实际理由，不凑测试数量。

## 阻塞（blocking）只有三种

- 功能未实现，或与需求相悖；
- 某条验收缺少其 verification 类型要求的证据，或对应检查失败；
- 可维护性问题有明确的需求影响和可核验凭据；纯风格或结构偏好只作建议。

每条阻塞指到具体的需求条目 / 验收标准与文件位置，并带凭据：`ac`（哪条验收标准没测试）与 / 或 `repro`（在当前树上会失败的测试或检查命令，修好后通过）。凭据在本树上站不住的，记待核实，不开 ISS。其余一律 advisory。只报影响正确性与需求达成的问题（C-41）。

现有 loop 的 ac-only 路径只查测试名映射，不判断证据质量；不要为满足它给文字凭空补“黑盒模型测试”。替身仍是 WARN，不是通过；真实人工验证缺失应如实保留，不伪造成自动化证据。

## 不做

- 不把所有边界输入一律禁止，也不强制穷举；只检查与需求及实际风险相关的情形；
- 不写攻击探针、不找攻击面；
- 不做突变验证；
- 不改代码、不改测试（C-39 / C-41）；
- 不主动审未修改的第三方框架；本任务修改的框架指令/代码应检查。消费项目 pack 可能只列框架文件名，省略的内容不能声称已审；keel 自身使用 review.self_hosted 包含内容。
