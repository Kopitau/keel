# 评审清单（REQ-028 v7 / DEC-191）

评审者只回答三个问题：读代码、读证据，最多把项目的测试命令跑一次（pack 里的证据对本树新鲜时连这一次也免）。不构造边界输入、不写探针、不做突变、不一轮轮重跑全量。

## 三问

1. **规范与可维护**：代码是否规范、尽量简单、别人能看懂能改。重复实现、无必要的抽象或复杂度、超出计划范围的改动、该给人话错误的地方给了裸堆栈，都算。风格与命名口味不算。
2. **功能是否实现**：diff 是否做了规划义务与需求条目说的事，有没有做规划禁止的事。对照 pack 里的 `plan` / `reqs` 读，不靠猜。
3. **功能测试是否写了、是否通过**：每条验收标准（`REQ-nnn/AC-i`）有一条真正的黑盒测试——名字带标记、只喂需求说的输入、只断言验收承诺的结果；证据 JSON 的 `feature_coverage` 逐功能列出黑盒 / 替身 / 缺失，`counts` 与 `exit_code` 说测试是否通过；跳过或删除的测试有工作日志理由（C-34）。

## 阻塞（blocking）只有三种

- 功能未实现，或与需求相悖；
- 某条验收标准没有黑盒测试，或测试不通过；
- 代码明显不可维护（第 1 问的实例）。

每条阻塞指到具体的需求条目 / 验收标准与文件位置，并带凭据：`ac`（哪条验收标准没测试）与 / 或 `repro`（在当前树上会失败的测试或检查命令，修好后通过）。凭据在本树上站不住的，记待核实，不开 ISS。其余一律 advisory。只报影响正确性与需求达成的问题（C-41）。

## 不做

- 不构造空 / 超长 / 非 ASCII / 极值输入去跑；
- 不写攻击探针、不找攻击面；
- 不做突变验证；
- 不改代码、不改测试（C-39 / C-41）。
