## REQ-001 需求访谈与记录

- **status**: confirmed
- **source**: docs/features.md F1；技术方案 C-02~C-07
- **feature**: F1
- **must**: 必需
- **description**: 新项目/新功能先结构化访谈：事实 agent 自查、取舍留给用户、每问附推荐、模糊处禁止脑补；收敛后形成带编号需求条目，未收敛不进设计。
- **acceptance**:
  - Given 本轮所有可问问题已齐 When 提问 Then 一次列出全部（编号+每题推荐）；有依赖的留下一轮；用户可切到一次一问（C-02）
  - Given 问题可从代码/文档/网络查清 When 访谈 Then 不问用户（C-03）
  - Given 一条需求 When 写入 Then 含 REQ 编号、状态、来源、描述、验收标准、边界与反例、非目标（C-04）
  - Given 验收标准 When 书写 Then 以 GWT 为主，简单条目可用 checklist（C-07）
  - Given 模糊点 When 记录 Then 标 [NEEDS-CLARIFICATION: 具体问题] 且未解分支进需求书「未决问题」节（C-05）
  - Given 大功能/新项目点头前 When 基线确认 Then 未参与访谈的新上下文先挑遗漏矛盾；用户整体点头一次=基线（C-06）
- **bounds_and_counterexamples**: 未收敛不得进设计。不问可自查事实。
- **non_goals**: 不把访谈做成平台私有命令。

## REQ-002 强制调研

- **status**: confirmed
- **source**: docs/features.md F2；技术方案 C-08~C-12
- **feature**: F2
- **must**: 必需
- **description**: 设计前必须调研，按风险分深度，产出带引用+日期的报告；不得零记录声称无需调研。
- **acceptance**:
  - Given 新架构/关键依赖/数据模型/安全/公共接口/跨平台/高不确定 When 调研 Then 深度档：≥2-3 候选+一手引用+反例（C-08）
  - Given 一份 RES When 落盘 Then 含问题/范围/候选/证据（引用+日期，未核实显式标）/结论三段/剩余不确定性，且通俗易懂（C-09）
  - Given 重大决策无 RES When 过 G-调研 Then 不通过，除非 DEC 写豁免理由（C-10）
  - Given 调研选用开源 When 结论落地 Then 强制建 OSS（C-11）
  - Given 离线 When 调研 Then 用带来源/版本/日期的离线资料或明确停下，禁止凭印象选型（C-12）
- **bounds_and_counterexamples**: 调研不是可选步骤。
- **non_goals**: 不把网页摘录整篇复制进 RES（引用而非复制，C-69）。

## REQ-025 全局安装器（在项目文件夹激活）

- **status**: confirmed
- **source**: 用户 2026-08-24「应该类似trellis，在项目文件夹激活，就相当于在这个文件夹部署了这个框架」；调研 RES-902；技术方案 DEC-157
- **feature**: F16 / F23
- **must**: 必需
- **description**: 提供全局 CLI（`keel init` / `update` / `uninstall` / `doctor`），作用于**当前目录**；装完后日常命令仍由项目内副本执行。分发是全局的，运行是本地的——原 DEC-153 的离线可用与版本随项目锁定两条理由全部保留。
- **acceptance**:
  - Given 一个空 git 仓库 When 跑 `keel init` Then 装完后 `gate check --quick` 只有 G-req/G-plan 未通过（且按 REQ-026 应为 SKIP），其余全绿
  - Given 已装过 keel 的目录 When 再跑 `keel init` Then 拒绝执行并提示改用 k-change / k-impl
  - Given Node 低于 22.18.0 When 跑任何 keel 命令 Then 打印「需要 Node ≥22.18.0」后退出，**不得出现语法错误**（bin 必须是纯 JS 薄壳，先查版本再 import .ts）
  - Given 装好的项目在 macOS/Linux When 提交时删掉一个测试 Then 被 hooks 拦住（证明可执行位已设对，ISS-004 的回归验证）
  - Given 跑完 `keel uninstall` Then `keel/` 记录目录完整存在，只有机器件被移除
  - Given 全局 CLI 版本低于项目内记录的 `keel_version` When 跑 `keel update` Then 警告并要求 `--force` 才继续
  - Given 目标目录检测到 `.trellis/` 或 superpowers 痕迹 When 跑 `keel init` Then 照常安装并提示「迁移旧记录请用 k-migrate（F22）」
  - Given `init` 时技术栈未定 When 写 config Then `profiles.active` 写 `unset` 并提示「技术方案确定后在统一规划中确认」；gate 在 `unset` 下必须优雅降级（verify 明确提示未配置测试命令），不得崩溃或静默通过
- **bounds_and_counterexamples**: `uninstall` 永不删记录（记录不可再生，误删无法恢复）；版本不一致只告知不强制同步；`init` 不做迁移、不做需求访谈。
- **non_goals**: 不做 CLI 自升级（用 `npm i -g` 原生）；不公开发布到 npm registry；不做跨项目版本锁服务；不在 `init` 里做需求访谈（那是 k-new）。

## REQ-026 空项目的门禁语义（G-req / G-plan 条件判定）

- **status**: confirmed
- **source**: 用户 2026-08-24 追问「G-req / G-plan 为什么会 fail」后确认「纳入」；技术方案 DEC-158
- **feature**: F17
- **must**: 必需
- **description**: G-req 与 G-plan 目前在「还没有需求书／规划」时一律 FAIL，与 G-done / G-retro / X-trace 的「无事可查则 SKIP」不一致，导致新装项目一上来就是红的，造成警报疲劳。改为条件判定：真正空的项目 SKIP，一旦出现实施活动却仍无基线则 FAIL。
- **acceptance**:
  - Given 项目确无实施活动（无 features 子目录内容、无 worklog、无完成声明）且无需求基线 When 跑 check Then G-req/G-plan 为 **SKIP**，摘要提示「尚未开始，跑 k-new 建立需求基线」
  - Given 存在任一实施活动（feature 目录 / worklog / summary）却无需求基线 When 跑 check Then G-req **FAIL**
  - Given 存在实施活动却无当前规划或规划缺「接口与耦合」表 When 跑 check Then G-plan **FAIL**
  - Given 已有需求基线且含未消解的 `[NEEDS-CLARIFICATION]` When 跑 check Then G-req 仍 FAIL（C-05 不变）
- **bounds_and_counterexamples**: 判定依据必须是**实施活动的客观痕迹**，不能靠 agent 自述；本改动只放宽「真空项目」这一种情形，其余判定一律不放宽。
- **non_goals**: 不放宽 C-05 的禁猜标记判定；不放宽 C-24 的耦合表要求。
