#### G-01　REQ-027/028 标 confirmed，但产生它们的变更单从未批准，而索引已经切过去了　【严重】

**现象**：需求书自己写着 CHG-008 还没批，同一份文件里的两条 REQ 却都是 confirmed，而且 INDEX 的 current 已经指向 v3。

**证据**：

- v3.md 第 10 行 note：「本文件亦含 REQ-027/028（CHG-008，仍 proposed）」；「未决问题」第 3 条：「CHG-008（REQ-027/028 自动评审回路）仍 proposed，尚未单独批准实施。」
- REQ-027、REQ-028 各自第一行都是 `- **status**: confirmed`。
- `keel/changes/CHG-008-auto-review-loop.md` frontmatter `status: proposed`，且 note 明写：「v3.md 由 CHG-007 与 CHG-008 共同产生，**二者一并批准后 INDEX 的 current 才切到 v3**」。
- `keel/requirements/INDEX.md`：`current: v3.md`。
- `keel/OVERVIEW.md`「在途功能」节：「**CHG-008 自动评审回路已实施**（`gate loop` + 三类清单），变更单仍 proposed。」

**为什么算缺口**：这直接违反 REQ-011 AC-2「Given CHG 批准 When 生效 Then 出新版需求+重索引」——顺序被倒过来了，先生效再等批准。同时 REQ-003 的边界写着「agent 不得自行把 proposed 标成 confirmed」，这里虽然标的是 REQ 不是 DEC，但性质一样。需求书自己承认「未批准」，却让两条 confirmed 需求驱动了一整套已上线的实现，任何后续评审都会把它们当基线用。

**去向建议**：二选一，**必须立刻选**。① 把 REQ-027/028 的 status 改回 proposed，直到用户批 CHG-008 并落 APR；或 ② 请用户当场批准 CHG-008 并落 APR，再把「未决问题」第 3 条销掉。另外**补一条门禁判据**：REQ 的 status 不得强于产生它的 CHG 的 status（现在 `gate check` 完全不查这个关系）。**立 ISS**。

#### G-02　REQ-019 与 DEC-155 正面冲突，v3 全文不含 DEC-155　【严重】

**现象**：需求说「一功能一分支一 worktree，强制」，同日确认的决策说「主线直接写就行，大功能才推荐开分支」。

**去向建议**：**改 REQ-019 AC-1**，写成三档判定，`source` 字段补 DEC-155；同步改 `AGENTS.md` 那一行。这条不改，任何读需求书的新上下文都会认为现在这些直接在 master 上的提交是违规的。

#### G-03　`keel update` 会静默覆盖文件，而 C-141 要求「先列覆盖清单 + 用户确认」——这条规则在 v3 里没有归属　【严重】

**现象**：C-141 是已确认决策，但它在 v3 里只出现在 REQ-023 的 `bounds_and_counterexamples` 里当背景说明；真正拥有 `update` 命令的 REQ-025，8 条验收标准里一条都没有它。实现因此是无清单、无确认的强制覆盖。

**证据**：

- DEC-141（confirmed）：「升级 = 脚本辅助拉新版文件（**先列将覆盖清单**）+ 用户确认执行；v1 不做自动升级与版本锁。」
- REQ-023 bounds：「消费项目升级 v1=tag+脚本列覆盖清单+用户确认，不做自动升级（C-141）」——写在边界字段里，不是验收标准，不可核验。
- REQ-025 的 8 条 AC：init 空仓、重复 init 拒绝、Node 版本、hooks 可执行位、uninstall 不删记录、update 版本低于项目时要 `--force`、`.trellis` 检测、`profiles.active=unset`。**没有一条约束 update 覆盖了什么。**
- 实现实证：`tools/cli/update.js:41` — `cpSync(src, join(cwd, rel), { recursive: true, force: true })`，无清单、无确认、无 dry-run。同文件第 17 行同样是 `force: true`。
- REQ-025 的 bounds 只护住了 uninstall：「`uninstall` 永不删记录（记录不可再生，误删无法恢复）」——同样的理由完全适用于 update，但没写。

**去向建议**：**补 REQ-025 AC**：`update` 执行前必须列出将被覆盖的文件清单并要求确认；`keel/` 记录目录在 update 下与 uninstall 同等受保护。**立 ISS** 跟进实现。这是本次找到的唯一一条有「不可恢复数据损失」风险的缺口。

#### G-04　`must` 三档（必需／建议／想要）与验收标准的强制力互相矛盾，且 v3 从未定义这三档是什么意思　【中】

**现象**：几条被标成「想要」「建议」的能力，被多条「必需」需求当成硬前置在用。

**证据**：

- REQ-017 门禁强制层 `must: 想要`；REQ-011 需求变更管理 `must: 想要`；REQ-007 独立评审 `must: 建议`。
- 但：REQ-006 AC-2「零引用=**门禁不过**」、REQ-008 AC-1「Given 合并 When 检查 Then 验收 APR+证据树哈希有效+追溯全绿」（由 gate 裁决）、REQ-009 AC-4「缺 summary… Then **门禁不许**」、REQ-011 AC-1「改当前 vN Then **门禁失败**」——四条「必需」级 REQ 的验收全部依赖那个「想要」级的门禁。

**去向建议**：**补需求**——在 v3 开头（「非目标」节旁边）加一节定义三档语义；并把 REQ-017、REQ-011 提为「必需」（它们事实上已经是），或者把依赖它们的 AC 显式降级。**改 REQ-007** 的 must 为「必需」以匹配 REQ-027/028，或把 REQ-027/028 降为「建议」。

#### G-05　REQ-027 要求自动开 ISS，REQ-010 要求 ISS 必须含「根因/修复/闭环选择」，而评审者「只报不改」——三条对不上　【中】

**去向建议**：**改 REQ-010**，区分 ISS 打开时的最小字段集（现象+复现命令+防线类型待定）与关闭时的完整字段集；或**改 REQ-027**，明确自动开的是 finding 级条目、诊断后才升为正式 ISS。二者选一，别让实现自己猜。
