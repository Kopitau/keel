## 验证方式

每条 REQ 的 `verification` 数组与 acceptance 按顺序一一对应（DEC-174）：

- `auto`：必须有只使用需求点名输入与结果的黑盒验收测试；白盒回归不能代替。
- `machine-doc`：流程/记录协议由可运行的结构或一致性检查验证，不冒充真人执行。
- `manual`：必须写明人工或真实环境的证据条件；替身只能标 `[proxy:<解除条件>]`，X-trace 记 WARN，不记 PASS。

功能出现 `summary.md` 才进入强制验收范围；未完成功能的缺口继续由 `gate trace` 显示，但不一律阻断日常施工。

  - Given Node 低于 22.18.0 When 跑任何 keel 命令 Then 打印「需要 Node ≥22.18.0」后退出，**不得出现语法错误**（bin 必须是纯 JS 薄壳，先查版本再 import .ts）
  - Given 装好的项目在 macOS/Linux When 提交时删掉一个测试 Then 被 hooks 拦住；人工证据记录 OS/版本、安装命令、hook 路径与可执行位、commit 命令、退出码和拦截输出（证明 ISS-004 回归已解除）
  - Given 跑完 `keel uninstall` Then `keel/` 记录目录完整存在，只有机器件被移除
  - Given 全局 CLI 版本低于项目内记录的 `keel_version` When 跑 `keel update` Then 警告并要求 `--force` 才继续
  - Given 任意 `keel update` When 执行 Then 先基于写入前快照完整列出新增、覆盖、删除及 legacy 清单条目变化，再直接询问 `y/N`；默认 N、非明确 y、stdin 不可用或 EOF 时，目标树连目录、临时文件、备份与元数据都零写入；明确 y 后也只执行已列出的操作（C-141/DEC-173/181）
  - Given 目标目录检测到 `.trellis/` 或 superpowers 痕迹 When 跑 `keel init` Then 照常安装并提示「迁移旧记录请用 k-migrate（F22）」
  - Given `init` 时技术栈未定 When 写 config Then `profiles.active` 写 `unset` 并提示「技术方案确定后在统一规划中确认」；gate 在 `unset` 下必须优雅降级（verify 明确提示未配置测试命令），不得崩溃或静默通过
- **verification**: [auto, auto, auto, manual, auto, auto, auto, auto, auto]
- **bounds_and_counterexamples**: `uninstall` 永不删记录；`update` 只触碰清单列出的框架管理文件并在确认前零写入；版本不一致只告知不强制同步；`init` 不做迁移、不做需求访谈。
- **non_goals**: 不做 CLI 自升级（用 `npm i -g` 原生）；不公开发布到 npm registry；不做跨项目版本锁服务；不在 `init` 里做需求访谈（那是 k-new）。

## REQ-026 空项目的门禁语义（G-req / G-plan 条件判定）

- **status**: confirmed
- **source**: 用户 2026-08-24 追问「G-req / G-plan 为什么会 fail」后确认「纳入」；技术方案 DEC-158
- **feature**: F17
- **must**: 必需
- **description**: G-req 与 G-plan 目前在「还没有需求书／规划」时一律 FAIL，与 G-done / G-retro / X-trace 的「无事可查则 SKIP」不一致，导致新装项目一上来就是红的，造成警报疲劳。改为条件判定：真正空的项目 SKIP，一旦出现实施活动却仍无基线则 FAIL。
- **acceptance**:
  - Given 项目确无实施活动（无 features 子目录内容、无 worklog、无完成声明）且无需求基线 When 跑 check Then G-req/G-plan 为 **SKIP**，摘要提示「尚未开始，跑 k-new 建立需求基线」
  - Given 存在任一实施活动（feature 目录 / worklog / summary）却无需求基线 When 跑 check Then G-req **FAIL**
  - Given 存在实施活动却无当前规划或规划缺「接口与耦合」表 When 跑 check Then G-plan **FAIL**
  - Given 已有需求基线且含未消解的 `[NEEDS-CLARIFICATION]` When 跑 check Then G-req 仍 FAIL（C-05 不变）
- **verification**: [auto, auto, auto, auto]
- **bounds_and_counterexamples**: 判定依据必须是**实施活动的客观痕迹**，不能靠 agent 自述；本改动只放宽「真空项目」这一种情形，其余判定一律不放宽。
- **non_goals**: 不放宽 C-05 的禁猜标记判定；不放宽 C-24 的耦合表要求。

## REQ-027 自动评审回路（F7 扩展）

- **status**: confirmed
- **source**: 用户 2026-08-24「审核应该少一点摩擦，应该可以让 agent 自动启动子 agent 进行审核然后落盘，让 agent 进行修复」；技术方案 DEC-159/160/177/178/182；CHG-008/010
- **feature**: F7
- **must**: 必需
- **description**: 把独立评审从「人工居间转手」变成自动回路：实现方声称完成时自动派干净上下文子代理评审 → 结论自动落盘 → 自动修 → 派**新的**子代理复审 → 直到 blocking 清零或熔断。用户的介入点由「每轮都要」降到「熔断时」与「清零后的验收」两处。C-39（评审者隔离）与 C-42（复审用新上下文）原则不变，本条只是把回路接起来。
- **acceptance**:
  - Given 实现方声称完成 When 未经评审 Then 不得进入验收；评审是完成的必经步骤（DEC-159 触发方式 A）
  - Given 派出评审子代理 When 提供输入 Then 只给 diff / 功能规划与测试义务 / 需求条目 / 证据 JSON / worklog 摘要五样，**不给实现过程的对话记录**（C-39 不变）
  - Given 改动触及门禁、证据或测试机制 When 评审 Then 按仓库 headless 配方**强制异构复审**；人工证据同时绑定实现与评审 harness 名称/版本、调用命令、输入包哈希、输出/退出码、日期与当前 tree hash；调用失败须显式停止，不得静默降级为同源；其余改动同源子代理即可（DEC-160）
  - Given 评审产出 blocking finding When ingest Then 只有带可运行攻击探针、在当前未修复树实跑退出 `0` 才自动开 open ISS，并填写 REQ-010 的打开态最小字段；缺命令或首次非 `0` 则降级为待核实 worklog，不得开 blocking ISS（C-58/DEC-182）
  - Given 一轮修复完成 When 复审 Then 由**新的**评审上下文实跑每条 ISS 的同一攻击探针；仍退出 `0` 表示问题仍可复现、不得 clear，只有变成非 `0`、表示原问题不再复现或原绕过被明确拒绝才可 clear；命令、结果、退出码、轮次/时间与当前 tree hash 追加进证据，不接受「看过觉得修好了」（DEC-182）
  - Given 同一条 blocking 修 3 轮仍未清零 When 第 3 轮结束 Then **熔断**，停止自动回路并向用户报告三轮各做了什么、为何未解决（呼应 C-60 三振熔断）
  - Given 平台无原生子代理（如 Pi） When 查执行协议 Then 仓库配方要求顺序开启不继承实现聊天的新会话、只交付规定输入包并回收结构化报告，不依赖任一平台私有能力（C-30 不变）
  - Given 平台无原生子代理 When 真实触发评审 Then 人工证据记录原会话与新评审会话的不同身份/时间、交付包哈希、启动命令或操作、报告路径、退出状态与 tree hash，证明不是同一上下文自审
  - Given 重复执行 `gate loop clear` When 写评审证据 Then `repro_runs` 按轮次或时间追加；没有新复现命令时保留历史，不得覆盖为空（DEC-177/ISS-036）
- **verification**: [auto, auto, manual, auto, auto, auto, machine-doc, manual, auto]
- **bounds_and_counterexamples**: 自动回路只覆盖到「blocking 清零」；**验收（A4）仍归用户**，不自动化。熔断阈值 3 轮为初值，可按实测调。
- **non_goals**: 不自动验收、不自动合并、不自动批准变更单；不因为回路自动化就放宽任何门禁判据。

## REQ-028 评审视角按代码性质分类

- **status**: confirmed
- **source**: 用户 2026-08-24「有些是功能实现，也需要攻击面么？很多时候只需要满足这个功能就行了，而不是假想会被攻击。或者说稳定性（鲁棒性如何）」；DEC-160/178；CHG-010
- **feature**: F7
- **must**: 必需
- **description**: 评审不应对所有代码套同一把尺。「攻击面」适用于框架自身的执法机制（门禁/证据/审批），普通功能代码该问的是鲁棒性。两者共享同一条纪律——**不只走 happy path，主动构造失败情形，且必须实证而非读代码推理**——但检查项不同。分类复用已确认的 C-31 测试分级，不另造轴。
- **acceptance**:
  - Given 被评审代码属门禁/证据/审批类 When 评审 Then 走**攻击面**清单：能否被单方面改变而不被察觉（改配置、伪造证据、缩范围、删测试、消警告、绕 hooks），且须在临时副本中实际尝试并记录复现命令
  - Given 被评审代码属 C-31 的**核心**级 When 评审 Then 走**鲁棒性**清单：边界输入（空/超长/特殊字符/非 ASCII/极值）、依赖不可用、脏数据、并发或重跑、**中途失败是否留下半成品状态**，且须实际构造这些输入运行
  - Given 被评审代码属 C-31 的**辅助**级 When 评审 Then 只查需求达成度与明显错误路径，不做深度鲁棒性测试
  - Given 任一类别 When 评审 Then 仍遵守 C-41「只报影响正确性与需求达成的问题」，不做吹毛求疵
  - Given 攻击面清单发现新的攻击方式 When 复盘 Then 追加到 `keel/review/attack-surface.md`，至少含攻击方式、复现命令、影响、防线指针与发现来源；历史项不删除（DEC-160/178）
- **verification**: [auto, auto, machine-doc, machine-doc, machine-doc]
- **bounds_and_counterexamples**: 分类由被改动文件的性质决定，不由实现方自述；跨类别的改动按最严的一类处理。
- **non_goals**: 不给辅助级代码做安全审计；不因分类而豁免任何已确认的测试义务。
