## 验证方式

每条 REQ 的 `verification` 数组与 acceptance 按顺序一一对应（DEC-174；长度不机检）。X-trace 对被认领功能绑定的每条 AC 一律要求下列之一，类型决定该用哪种：

- `auto`：只使用需求点名输入与结果的黑盒验收测试，测试名带 `REQ-nnn/AC-i`（DEC-168）；白盒回归不能代替。
- `machine-doc`：可运行的协议/记录一致性检查（读技能、模板、配方文本或跑一遍协议），同样以 `REQ-nnn/AC-i` 命名；不冒充真人执行。
- `manual`：写明人工或真实环境的证据条件；机器侧只能是 `[proxy:<解除条件>]` 替身，X-trace 记 WARN，不记 PASS。

功能出现 `summary.md` 才进入强制验收范围；未完成功能的缺口继续由 `gate trace` 显示，但不阻断日常施工。

## REQ-027 方案级评审回路（F7 扩展）

- **status**: confirmed
- **source**: 用户 2026-08-24「审核应该少一点摩擦…」；用户 2026-08-29「子agent审核不用每个功能都审核，而是整个技术方案都实现了再进行审核」；技术方案 DEC-159/160/177/178/182/183；CHG-008/010/011
- **feature**: F7
- **must**: 必需
- **description**: 统一规划内全部功能实现后（都有 summary）派一轮空白上下文子代理评审 → 发现清单落盘 → 修 → 派**新的**子代理复审 → 直到 blocking 清零或三轮熔断。功能级不再派评审，只有自测与证据。用户介入点：熔断时与清零后的验收。C-39 / C-42 原则不变。
- **acceptance**:
  - Given 统一规划内全部功能都有 `summary.md` When 进入验收 Then 先派一轮方案级评审；单个功能完成不触发评审（DEC-183）
  - Given 派出评审子代理 When 提供输入 Then 只给 diff / 规划与测试义务 / 需求条目 / 证据 JSON / worklog 摘要五样，**不给实现过程的对话记录**（C-39）
  - Given 改动触及门禁、证据或测试机制 When 评审 Then 按仓库 headless 配方**强制异构复审**；人工证据同时绑定实现与评审 harness 名称/版本、调用命令、输入包哈希、输出/退出码、日期与当前 tree hash；调用失败须显式停止，不得静默降级为同源；其余改动同源子代理即可（DEC-160）
  - Given 评审产出 blocking finding When ingest Then 只有带可运行攻击探针、在当前未修复树实跑退出 `0` 才自动开 open ISS；缺命令或首次非 `0` 则降级为待核实，不得开 blocking ISS（C-58/DEC-182）；探针根本无法执行（外壳/解释器失败）则回路停在 in_review、clear 拒绝，直到新一轮给出能跑的探针（ISS-054）
  - Given 一轮修复完成 When 复审 Then 由**新的**评审上下文实跑每条 ISS 的同一攻击探针；仍退出 `0` 不得 clear，变成非 `0` 才可 clear；命令、结果、退出码、轮次与 tree hash 追加进处置表（DEC-182）
  - Given 同一条 blocking 修 3 轮仍未清零 When 第 3 轮结束 Then **熔断**，停止自动回路并向用户报告三轮各做了什么、为何未解决（C-60）
  - Given 平台无原生子代理（如 Pi） When 查执行协议 Then 仓库配方要求顺序开启不继承实现聊天的新会话、只交付规定输入包并回收结构化报告（C-30）
  - Given 平台无原生子代理 When 真实触发评审 Then 人工证据记录原会话与新评审会话的不同身份/时间、交付包哈希、启动命令或操作、报告路径、退出状态与 tree hash
  - Given 重复清零 When 写处置表 Then 按轮次追加，不覆盖历史（DEC-177/ISS-036）
  - Given 评审产物 When 落盘 Then 每轮评审产物只有 `keel/review/findings.md`（发现清单）与 `keel/review/disposition.md`（处置表，含 plan 版本、轮次、状态 passed/repairing/fused）两份 markdown（攻击面清单与 headless 配方是长期知识文件，不属评审产物）；G-done 读处置表：passed → PASS，repairing → WARN，fused → FAIL；处置表缺失时，仍有已认领功能无 summary → PASS（施工中），全部功能已有 summary → FAIL「方案实现完，评审未跑」（CHG-011）
- **verification**: [auto, auto, manual, auto, auto, auto, machine-doc, manual, auto, auto]
- **bounds_and_counterexamples**: 自动回路只覆盖到「blocking 清零」；**验收仍归用户**。用户已接受"缺陷到方案末尾才发现"的代价（DEC-183）；连续两次在末尾发现"早该在第一个功能抓到"的缺陷时复审本条（DEC-183 复审条款）。
- **non_goals**: 不自动验收、不自动合并、不自动批准变更单；不因为回路自动化就放宽任何门禁判据。

## REQ-028 评审视角按代码性质分类

- **status**: confirmed
- **source**: 用户 2026-08-24「有些是功能实现，也需要攻击面么？…」；DEC-160/178；CHG-010
- **feature**: F7
- **must**: 必需
- **description**: 评审不应对所有代码套同一把尺。「攻击面」适用于框架自身的执法机制（门禁/证据/审批），普通功能代码该问的是鲁棒性。两者共享同一条纪律——**不只走 happy path，主动构造失败情形，且必须实证而非读代码推理**——但检查项不同。分类复用已确认的 C-31 测试分级，不另造轴。
- **acceptance**:
  - Given 被评审代码属门禁/证据/审批类 When 评审 Then 走**攻击面**清单：能否被单方面改变而不被察觉（改配置、伪造证据、缩范围、删测试、消警告、绕 hooks），且须在临时副本中实际尝试并记录复现命令
  - Given 被评审代码属 C-31 的**核心**级 When 评审 Then 走**鲁棒性**清单：边界输入（空/超长/特殊字符/非 ASCII/极值）、依赖不可用、脏数据、并发或重跑、**中途失败是否留下半成品状态**，且须实际构造这些输入运行
  - Given 被评审代码属 C-31 的**辅助**级 When 评审 Then 只查需求达成度与明显错误路径，不做深度鲁棒性测试
  - Given 任一类别 When 评审 Then 仍遵守 C-41「只报影响正确性与需求达成的问题」，不做吹毛求疵
  - Given 攻击面清单发现新的攻击方式 When 复盘 Then 追加到 `keel/review/attack-surface.md`，至少含攻击方式、复现命令、影响、防线指针与发现来源；历史项不删除（DEC-160/178）
- **verification**: [auto, auto, machine-doc, machine-doc, machine-doc]
- **bounds_and_counterexamples**: 分类由被改动文件的性质决定，不由实现方自述；跨类别的改动按最严的一类处理。
- **non_goals**: 不给辅助级代码做安全审计；不因分类而豁免任何已确认的测试义务。
