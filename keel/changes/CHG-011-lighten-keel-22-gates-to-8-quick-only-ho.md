# CHG-011 keel 减重：门禁 22 → 8、预提交只跑秒级检查、冻结只管语义、记录三合一、方案级评审、测试按功能

## 动机

用户 2026-08-29："感觉目前的架构很沉重，让 agent 运行代码的时候经常会有摩擦，效率很低。同时结果汇报也不清晰。是不是记录和验证的部分有过度设计？"

实测（当日仓库）：门禁 22 个检查、gate 6005 行 / 45 文件、321 条自测；记录 183 DEC / 53 ISS / 16 RES / 11 CHG；18 个模板；本周三次提交里记录+技能文件数为 9 / 7 / 46，对应代码+测试 13 / 4 / 8；消费项目 zhaoxi 的 F0 产品代码 3041 行，对应测试 3700 行、过程记录 1777 行 + 423 KB 评审 JSON，五轮评审后仍无一个用户可用功能。

摩擦来源（本周亲历）：每出一次事故加一条机器规则，规则再配正样本测试，误杀三次（ISS-038、RES-901/902、zhaoxi 八份 RES）；同一件事写四遍（DEC、两份 worklog、handoff、提交信息）；不可变用到元数据（补两行前言要 CHG + 九份 v2 + APR）；工作树一脏全检必红，红灯常态化；预提交跑全量测试并两次因钩子自身环境出事（GIT_DIR、GIT_AUTHOR）；测试名基线让每次合法改名都要引用记录；评审每功能多轮、产物几百 KB。汇报不清晰：编号混排、门禁输出无人话结论、证据术语直接给人看。

诊断与用户裁决（DEC-183）：**原则不变，机制砍半**。用户逐条答复：门禁留骨架（乙）、预提交改秒级、冻结只管语义、记录三合一、评审改为整个技术方案实现完再审并接受"缺陷到末尾才发现"的代价、技能不合并、测试按验证功能且对话里定下的小功能也要测。

## 删除

1. **门禁 14 条**：G-research、G-retro、X-budget、X-skills、X-casefold、X-ids、X-types、X-hooks、X-oss、X-knowledge、X-tests、X-full、X-owners、X-decisions。连同其专属模块（rescheck / gaphunt / candidates / osscheck / knowledge / testbase / execmode / decisions / changechain / lessons / autoload / skills 检查部分）与自测一并删除；`gen-test-baseline` 与 `keel/test-baseline.json` 删除；`migrations/res-citation-legacy.json` 删除。
2. **预提交跑全量测试**（DEC-162）：撤销。钩子只跑 `check --quick`（8 条，秒级）与审批身份守卫（DEC-167 保留）。类型检查与全量测试只在 `gate verify` 与 CI。
3. **测试名基线 / C-34 机检**：删除。"删测试骗绿"改由 X-trace（宣称完成时 AC 无黑盒测试即 FAIL）与方案级评审承担。
4. **模板 10 个**：GAPHUNT、LES、KLES、OSS、journal、handoff、evidence.json、requirements-entry、migrate/ 三份映射表；`config.json` 从模板移到安装器。保留 8 个：DEC、ISS、RES、CHG、APR、feature-plan、worklog、summary。
5. **记录种类**：journal 目录；LES / KLES / OSS 独立文件（经验一行进 worklog 或 DEC；OSS 写在 RES 的 `oss:` 字段；跨项目知识库改为可选的 `~/.keel/knowledge/` 纯文本，不机检）；缺口猎取不再单独成文件（写在需求书"未决问题"之后一段）；评审目录的 pack.json / state.json / rounds 账本（评审产物 = 发现清单 + 处置表两份 markdown）。
6. **DEC 的机检**：研究指针（C-10）、状态机（X-decisions）、验证数组长度（DEC-174 的 G-req 分支）不再机检，降为技能规则。
7. **功能级子代理评审**：不再每功能派评审。

## 修改

- **C-24 / C-63 / C-106 冻结范围**：只管语义。前言元数据、错字、索引、链接修正原地改，不走 CHG；语义变仍走 CHG + 新版本。
- **C-17 / C-16 决策粒度**：只有同时满足"难逆转 + 无上下文会意外 + 真权衡"的决策写 DEC；其余实现决定一行进 worklog。
- **C-20 / C-52 / C-70 记录三合一**：worklog 是唯一过程记录；handoff ≤ 10 行（下一步 + 该读文件）；summary 只在功能验收时写一次，含"做了什么 / 技术路线 / 测试与证据 / 遗留"四段。
- **C-33 证据新鲜度**：只在宣称完成（summary）与合并前判；日常工作树脏不红。
- **C-35 红灯证据**：只要求修 bug 的回归测试"无补丁挂、有补丁过"；新功能测试不要求先红。DEC-013 的突变验证只对修复类测试，作为 k-bugfix 技能规则，不机检。
- **C-39 / C-42 评审时机（REQ-027 / REQ-028）**：统一规划内全部功能都有 summary 后派一轮空白上下文评审（异构可选）→ 发现清单 → 修 → 一轮复审 → 三轮未清熔断。功能级只有自测 + 证据。攻击面 / 鲁棒性两种视角（REQ-028）保留，用于这一轮。
- **C-100 / C-102 钩子**：pre-commit = quick + 审批守卫；pre-push = 提醒；CI = 权威。
- **C-118~C-123 预算**：不机检；数字写在 AGENTS.md 与技能文字里作为约定。
- **C-06 缺口猎取**：保留为 k-grill 的一步（新项目基线前由空白上下文猎一遍），结果写进需求书，不机检。
- **C-08~C-12 调研**：RES 仍须写（问题 / 范围 / 证据带引用与日期 / 结论），不机检实质。
- **汇报层**：`gate status` 前三行人话（能否提交 / 缺什么 / 下一步）；`gate check` 只打印非 PASS 项与一行总结；技能与记录用名字，编号放括号。
- **REQ-006 测试**：每个实现了的功能——包括对话中临时定下的小功能——须有验证该功能行为的黑盒测试，测试名带 `REQ-nnn/AC-i`（DEC-168 的黑盒 / 白盒 / proxy 命名保留）；对话中定下的小功能在当前功能计划的"内部步骤"追加一条（C-23 规划补充，不开 CHG）并配测试。
- **必要级下调为"想要"**：REQ-013 摩擦沉淀、REQ-014 跨项目知识库、REQ-015 开源登记（改为 RES 字段）、REQ-020 上下文预算。
- **REQ-026** 并入 G-req / G-plan 的语义（空项目 SKIP，有实施活动无基线 FAIL），不再单列。
- **REQ-016**：16 个技能全部保留，正文各减到核心步骤（≤ 80 行），删掉对已删门禁的引用；`agents/openai.yaml` 由 `gate sync` 生成，不机检。
- **REQ-017**：门禁 = 8 条：G-req、G-plan、G-done、G-merge、X-trace、X-evidence、X-bypass、X-apr。

## 新增

- **自主实施回路（用户 2026-08-29 重点说明，REQ-004 / REQ-006 / REQ-007 / REQ-012 各一条 AC）**：需求、功能与技术方案尽量与用户确认并记录（k-new 一次点头）；确定之后人少参与或不参与——agent 实现一个功能 → 跑测试 → 测试通过后记录证据 → **功能完成时把 worklog 压缩进 summary（或按功能分割）** → 自动进入下一个功能（新上下文只读压缩后的记录与计划，不带上一功能的过程）→ 重复 → 全部完成后由子代理评审 → 用户验收。人只在三处出现：技术或功能不确定（C-21 停下问）、断点续传（新会话开场）、最终验收。k-impl 昨日借入的"一个会话一个切片，切完就停"改为"切完就继续"；交接只在上下文将满或功能完成压缩时写。
- `gate status` 人话三行；`gate check` 精简输出（REQ-017 / REQ-005 各一条 AC）。
- REQ-006 新 AC：对话中新增的小功能有计划落点与黑盒测试。
- REQ-027 新 AC：方案级评审的触发（全部功能 summary 就位）、产物（`keel/review/findings.md` + `disposition.md`）、熔断（三轮）。
