# 框架功能清单（已定稿）

> 定稿日期：2026-08-21（对话逐条确认制下由用户确认）
> 框架名称：暂用代号 keel，正式名称待后续条目确认
> 本文件是功能层的唯一事实源；每条功能的技术方案随对话逐条确认后，记入 docs/decisions.md 并落进 DESIGN.md

## 第一组 · 流程主干

### F1 需求访谈与记录【必需】
新项目/新功能先结构化访谈：事实 agent 自查、取舍留给用户、每问附推荐、模糊处禁止脑补；收敛后形成带编号需求条目，未收敛不进设计。

### F2 强制调研【必需】
设计前必须调研，按风险分深度（本地/标准/深度），产出带引用+日期的报告；不得零记录声称"无需调研"。

### F3 技术方案逐条确认 + 决策账本【必需】
每个技术决策单独呈报（推荐+理由+备选+引用），用户逐条表态、当场记录；未拍板先推进的记"暂定"，带理由+复核触发条件。

### F4 统一实施规划（技术方案落地时）【必需】
- 时点：F3 技术方案逐条确认完、方案落地前，作为设计收尾；
- 内容：对**所有功能统一规划**——功能清单与边界、功能间接口与耦合、依赖与实施顺序、各功能测试义务、此刻能定的内部大致步骤；能定的都在这一份里定掉；
- 确认：与技术方案基线一起**统一确认一次**；之后各功能开工不再单独审批计划；
- 执行：agent 自主推进（内部分解/顺序/手段自定），**实施过程落盘**（分解、进度、非显然选择的理由随做随记）；触碰已确认的接口/需求/方案边界才升级回用户；
- 中途新增功能：走 F11 变更单，实施规划在变更单里补充确认。

### F5 框架开销控制【必需】
生成代码等实际工作该消耗多少 token 就消耗多少；**模型智能与功能实现优先，省 token 不以牺牲两者为代价**。只省"框架税"且只用不损智的手段：
1. 状态查询、门禁裁决、追溯核对 = 确定性脚本，0 token；
2. 常驻注入小（根指令短、技能正文按需加载）——平台硬限所迫（Codex 32KiB 截断）；
3. 上下文清单是**导航建议不是枷锁**，模型认为需要读更多就读更多；
4. 记录模板只是骨架便利，模型自由书写，不限篇幅形式；
5. 证据默认摘要+关键输出，全量日志进 CI 附件，需要可查全量。

### F6 测试与完成证据【必需】
功能↔测试可追溯（需求编号进测试标记）；"完成"只认机器可核验证据（命令+退出码+输出+代码树哈希，代码一变旧证据作废）；门禁实际重跑测试对账，拦截谎报；测试分级（核心先测后码/辅助后补/豁免留痕）。

### F7 独立评审与人工验收【建议】
新上下文评审者（可异构模型）对照需求与计划审 diff，只报正确性问题；然后用户按验收摘要验收。

### F8 合并/集成车道【必需（含 no-mistakes 评估）】
验收通过才许合并；rebase/推送保护/自动 PR/CI 盯梢。no-mistakes（kunchenguid/no-mistakes，MIT）评估结论：可作可选组件（门禁配进其流水线、其对抗性 review 充当 F7）；CI 复算仍是权威；Gitee 无 PR/CI 步。

### F9 复盘与功能级总结【必需】
每功能完成强制两层总结：**功能总结**（做了什么/为什么/**技术路线说明**（架构与选型、数据流、为什么这么走，引用决策与调研）/关键决策/证据指针/遗留债务）+ **项目总览**（活文档：项目现状、整体技术路线图、能力清单、在途任务）；新会话开场必读总览。不含花费说明。

## 第二组 · 记录与知识

### F10 问题日志与防复发闭环【必需】
问题当场记（现象/复现/根因/修复/为何未被更早发现）；归档前每条闭环成回归测试/lint/hook/规则/决策修订之一，或显式不修+理由。

### F11 需求变更管理【想要】
实现期需求只读，改需求走变更单（增改删+影响评估）→用户批→联动更新+受影响证据作废。

### F12 会话交接/断点续传【想要】
会话收尾更新交接文件；新会话开场先跑状态脚本再读交接（实证：上下文压缩后模型自主记忆失效，状态必须从文件拉）。

### F13 摩擦沉淀（经验观察者）【必需】
非阻断观察机制：从用户纠正、同一错误指纹反复出现、旧防线失效、评审发现、知识缺口生成**经验候选**；不打断当前工作，在自然边界（复盘/问题闭环/评审后）核实后才沉淀为正式项目经验；同一指纹同功能 ≥3 次才算 repeated failure，不因错误总数自动升级。

### F14 跨项目知识库【必需】
项目内经验/规范/踩坑可提升（脱敏、泛化）到用户级跨项目知识库；新项目初始化与会话开场可引用；跨项目知识只是候选参考，进入某项目的正式规则仍走该项目自己的确认。

### F15 开源复用登记与追踪【必需】
调研或实施中直接复用开源项目（依赖/借鉴/改造/fork/模板）必须登记：项目名、仓库地址、精确版本或 commit、许可证、复用方式、复用点（哪个功能哪些文件）、本地改动差异、**追踪计划**（新版本/安全公告/上游修复）、复查周期与下次复查日期。定期只读复查上游，产出"无变化/关注/建议调研/建议变更"结论——只提示不自动动代码，升级走 F11。与 F2 衔接（调研选用→强制建条目）、与 F9 衔接（功能总结引用条目）。

## 第三组 · 平台与工程

### F16 六平台适配【必需】
一份 AGENTS.md + 标准技能目录五家零适配（Codex/OpenCode/Pi/Grok Build/DeepSeek Harness），Claude Code 一行桥+镜像；流程逻辑全在技能层，零平台私有命令。

### F17 门禁强制层【想要】
五层：指令→平台钩子→git hooks→**CI 复算（权威）**→人工审批；一个零依赖脚本五处共用。

### F18 审批记录机制【建议】
审批留不可伪造记录（内容哈希+人类身份提交+目录保护）；吸收"规范摘要哈希"（改错字不作废审批）。

### F19 多人团队 + 多 agent 并行【想要】
一功能一分支一 worktree；接口耦合在 F4 统一规划先定，文件所有权重叠即串行；提交尾注记 agent/模型/会话；合并走 PR+人批。

### F20 上下文预算控制【想要】
指令文件行数/字节上限进 CI 检查（Codex 32KiB 硬截断实证）；记录永不自动注入。不含花费记账。

### F21 语言与项目类型配置【想要】
agent 指令英文/面向人的记录中文；测试基座按项目类型配置（pytest / nbmake+数据校验 / Playwright；探索 notebook 豁免、沉淀成管道必须补测试）。

### F22 既有框架迁移【必需｜2026-08-21 增补】
项目此前在用 Trellis、Superpowers 等流程框架的，接入 keel 时把旧框架的既有内容**转换生成 keel 的对应关键文件**（需求书、统一规划、功能目录、决策、问题、总览、交接等），而非丢弃历史从零开始；同时**挖掘项目 docs/ 等不规范内容**中的规划设计与规则，一并转换。迁移产物一律是"未确认初稿"，走 keel 正常确认流程；只读源不破坏；出迁移报告；完成后旧框架技能/钩子经用户确认停用（双框架互斥）。
（与 N2 边界：N2 指从存量**代码**扫描生成基线，仍留 v2；F22 是从旧框架**流程工件与项目文档**迁移，纳入 v1。）

### F23 框架自举（自己管理自己）【必需｜2026-08-21 增补】
keel 仓库自身的后续开发用 keel 自己的流程管理：设计阶段产物按 F22 方式迁入自身记录（保留编号映射）；改 gate/技能/模板由**主干现行版 gate 在 CI 裁决**（上一版管下一版，防自举悖论）；框架形态的测试政策适配（gate=`node:test`（DEC-152）、技能=无歧义测试+触发实测、整体验收=冒烟项目全流程）；演化走 F1~F11 全流程，破坏性变更须 adr 决策+变更单；消费项目升级 v1 从简（tag+脚本辅助复制+用户确认）；本轮对话记录被认定为 keel 的第一批正式账本。

### F24 跨平台支持（Windows + macOS + Linux）【必需｜2026-08-21 增补，CHG-001】
三平台均为一等公民：Windows / macOS 为开发机，Linux 为 CI 运行环境（CI 复算是唯一权威门禁，本就跑在 Linux runner 上）。要点：① 哈希一律在规范化内容（LF、UTF-8 无 BOM）上计算，并以 `.gitattributes` 强制 `eol=lf`——否则 CRLF/LF 差异会击穿审批哈希与证据哈希；② 路径用运行时 API、文件名统一小写连字符，CI 检查大小写冲突（Linux 敏感、Mac/Win 不敏感）；③ 双启动器 `gate.sh`/`gate.ps1` 自动探测运行时，git hooks 用 `#!/bin/sh` 薄壳；④ 技能镜像三平台一律复制不用软链；⑤ 同一 fixture 在多平台必须产出相同门禁结论、哈希与追溯矩阵，CI 矩阵加 macOS runner。
macOS 上平台体验更好：OpenCode 原生可用、DeepSeek Harness 完整可用（Windows 分别需 WSL／受限）。
